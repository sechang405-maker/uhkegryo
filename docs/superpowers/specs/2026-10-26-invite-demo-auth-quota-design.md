# 초대형 데모 인증·누적 AI 사용량 설계

> **상태:** 기본 설계 승인 · 단계별 구현 중
> **범위:** 약 10명의 초대 사용자가 운영자 비용으로 데모를 사용하도록 Google 로그인, 이메일 허용 목록, 계정별 누적 AI 요청 횟수를 추가한다.

## 1. 목적과 확정 정책

이 데모는 불특정 다수 공개 서비스가 아니다. 운영자가 초대한 소수 사용자가 로그인하여 각자의 대화와 개인 용어를 사용하고, 운영자는 계정별 AI 사용 가능 횟수와 전체 비용 위험을 통제한다.

확정된 정책은 다음과 같다.

- Google 로그인만 제공한다.
- Google이 검증한 이메일이 초대 목록에 있어야 서비스에 들어올 수 있다.
- 사용량은 계정별 **누적 AI 요청 횟수**이며 날짜 변경이나 새 대화 생성으로 초기화하지 않는다.
- 일반 AI 대화와 개인 용어 AI 초안 생성은 각각 성공 시 1회 차감한다.
- 서버가 즉시 반환하는 고정 안내와 이미지 재검색은 차감하지 않는다.
- 실패한 요청, 같은 idempotency key의 중복 제출, 한 요청 안의 내부 자동 재시도는 추가 차감하지 않는다.
- 계정마다 서로 다른 한도를 둘 수 있다. 실제 지급 숫자는 나중에 정한다.
- 신규 계정은 누적 한도 0으로 시작하며 관리자가 명시적으로 지급한다.
- 기존 대화별 20회 제한은 대화 길이 제한으로 유지하고, 계정 누적 한도는 새 대화에서도 이어진다.
- 초대·계정 차단·한도 조정은 관리자만 수행한다.

초대 이메일, 도메인 제한, 계정별 한도 숫자, 전체 운영 예산, 호스팅, OpenRouter 모델은 아직 정하지 않는다.

## 2. 비범위와 실패 조건

이번 기능에 포함하지 않는다.

- 공개 회원가입, 비밀번호 로그인, 결제·충전, 조직·팀 기능
- Google 계정 간 데이터 이전이나 익명 데이터를 자동 병합하는 기능
- 실패한 공급자 호출 비용을 사용자에게 금액으로 청구하는 기능
- 이미지 검색을 AI 쿼터로 계산하는 기능
- OAuth 앱 등록, 실제 자격 증명 발급, 공개 배포

다른 사용자의 대화·개인 용어가 보이거나, 중복 클릭과 내부 재시도로 여러 번 차감되거나, 새 대화로 한도를 우회할 수 있으면 설계 실패다.

## 3. 현재 구현과 바뀌는 경계

현재 서버는 `backend/shared/auth.py`의 HttpOnly `session_id` 쿠키를 해시하여 `anonymous_owners`를 찾는다. `sessions`와 `personal_terms`는 이미 `owner_id`를 통해 분리된다. `backend/services/session_usage.py`와 `JobRepository._submit()`은 한 대화에 생성된 모든 job을 세어 20건에서 차단한다. 이 값은 성공 여부나 실제 LLM 호출 여부를 구분하지 않는다.

따라서 대화·개인 용어의 기존 `owner_id` 관계는 보존하고, 인증 계정과 쿼터만 그 위에 추가한다. 클라이언트가 보낸 이메일이나 owner ID를 권한 근거로 사용하지 않는다.

## 4. 인증 방식 대안

### A. FastAPI가 Google OIDC와 앱 세션을 소유 — 권장

FastAPI가 로그인 시작·콜백·로그아웃을 처리하고, Google ID Token을 검증한 뒤 자체 불투명 앱 세션 쿠키를 발급한다. Next.js는 `/api` 프록시와 로그인 상태 표시만 맡는다.

- 장점: 현재 FastAPI의 owner 검사와 DB 트랜잭션 경계를 그대로 확장할 수 있다.
- 단점: 검증된 OAuth/OIDC 클라이언트 의존성 하나와 콜백 라우트가 필요하다.
- 권장 이유: API·개인 용어·쿼터가 모두 FastAPI/PostgreSQL에 있으므로 인증 판단이 한 서버에 남는다.

### B. Next.js/Auth.js가 로그인 소유

Next.js가 세션을 만들고 FastAPI가 서명 토큰을 매 요청 검증한다.

- 장점: 로그인 UI 통합이 편하다.
- 단점: 현재 프런트는 단순 프록시인데 인증 서버 역할까지 갖게 되고, Next.js와 FastAPI 사이 토큰 계약·키 회전·로그아웃 동기화가 추가된다.

### C. 관리형 인증 서비스

- 장점: 초대·사용자 관리 화면을 빨리 얻을 수 있다.
- 단점: 새 외부 서비스, 비용, 벤더 의존성과 데이터 경계가 생긴다.

FastAPI가 Google OIDC와 앱 세션을 소유하는 A안을 채택한다. 실제 OIDC 클라이언트 라이브러리와 Google 자격 증명은 인증 단계에서 별도로 검토·설정한다.

## 5. 데이터 모델

기존 테이블을 삭제하거나 개인 용어를 공용 카탈로그로 옮기지 않는다. additive migration으로 다음 구조를 제안한다.

### `accounts`

- `account_id UUID PRIMARY KEY`
- `google_subject TEXT UNIQUE NOT NULL`: 이메일 변경과 무관한 Google 계정 식별자
- `email_normalized TEXT UNIQUE NOT NULL`; 검증 여부는 Google OIDC 콜백에서 확인하며 미검증 이메일은 저장소에 전달하지 않는다.
- `display_name TEXT`, `role`(`user`, `admin`), `status`(`active`, `disabled`)
- `ai_request_limit BIGINT NOT NULL`, `created_at`, `last_login_at`

### `invites`

- 정규화한 이메일, `status`(`pending`, `accepted`, `revoked`), 생성·수락 시각
- 초대 여부는 Google이 검증한 이메일과 서버에서만 비교한다.

### `auth_sessions`

- 앱 세션 토큰의 해시, `account_id`, 만료·폐기·최근 사용 시각
- 브라우저에는 원문 토큰을 HttpOnly·Secure·SameSite=Lax 쿠키로만 보낸다.

### 기존 owner 연결

`anonymous_owners`에 nullable unique `account_id`를 추가한다. 로그인 계정당 owner 하나를 보장하고 기존 `sessions.owner_id`와 `personal_terms.owner_id`는 그대로 둔다. 테이블 이름은 과거 구조를 반영하지만 첫 구현에서 대규모 rename은 하지 않는다.

### `ai_usage_operations`

- `operation_id`, `account_id`, `operation_kind`(`conversation`, `personal_term_proposal`)
- `idempotency_key_hash`, 관련 `job_id` 또는 `personal_term_id`
- `state`(`reserved`, `charged`, `released`), `reserved_at`, `finalized_at`
- 계정·작업 종류·idempotency key에 unique 제약을 둔다.
- 운영 관측용으로 공급자 시도 횟수와 반환된 토큰 사용량을 별도 기록할 수 있지만, 이를 사용자 차감 횟수로 사용하지 않는다.

쿼터의 권위 있는 값은 `charged` 개수이며, 동시 요청 가능 여부는 `charged + reserved < ai_request_limit`으로 판단한다.

## 6. 로그인·권한 흐름

1. 사용자가 로그인 버튼을 누르면 서버가 state, nonce와 PKCE 값을 생성하고 짧게 만료되는 서버 저장소에 보관한다.
2. Google 콜백에서 state·nonce·PKCE·발급자·audience·서명·만료를 검증한다.
3. `email_verified=true`이고 정규화 이메일이 유효한 초대에 있을 때만 계정을 생성하거나 갱신한다.
4. 비활성 계정과 취소된 초대는 로그인 및 기존 세션 사용을 차단한다.
5. 서버는 불투명 앱 세션을 발급하고 account → owner를 해석한다. 이후 모든 대화·개인 용어·쿼터 API는 이 owner를 서버에서 구한다.
6. 로그아웃은 앱 세션을 DB에서 폐기하고 쿠키를 만료한다.

OAuth 콜백만으로 상태 변경을 허용하지 않는다. 기존 `Origin`/`Sec-Fetch-Site`/동작 헤더 검사와 더불어 상태 변경 API에 CSRF 방어를 유지한다. 액세스 토큰이나 Google ID Token을 브라우저 저장소에 보관하지 않는다.

## 7. 쿼터 차감 상태 기계

```text
요청 수락 → LLM 필요 여부 결정
  ├─ 고정 안내·이미지 재검색 → 쿼터 원장 없음
  └─ LLM 필요 → DB 원자적 예약
       ├─ 한도 부족 → 공급자 호출 전 429
       ├─ 유효 결과 저장 성공 → charged 1회
       └─ 최종 실패 → released
```

- 대화 job은 worker가 실제 모델 호출을 시작하기 직전 예약한다.
- 개인 용어 초안은 generator가 모델 호출 직전 예약하고, 검증된 proposal을 저장한 뒤 차감한다.
- 자동 재시도는 같은 operation을 재사용한다. 새 reservation을 만들지 않는다.
- 같은 idempotency key의 재제출은 기존 결과 또는 상태를 반환한다.
- 모델은 성공했지만 결과 저장이 실패하면 사용자 차감은 하지 않는다. 실제 공급자 비용은 운영자 비용 관측에 남는다.
- 프로세스 중단으로 오래 남은 reservation은 job/proposal의 최종 상태와 대조하는 복구 작업이 `charged` 또는 `released`로 결정한다. 시간만 보고 무조건 해제하지 않는다.
- 이미지가 일부 실패해도 유효한 AI 해석이 저장되었다면 AI 요청은 성공으로 본다. 이미지 재검색은 추가 차감하지 않는다.

사용자 쿼터와 운영자 실제 비용은 별도다. 공급자 실패도 비용을 만들 수 있으므로 계정 쿼터 외에 전체 동시 호출 제한, IP·계정별 속도 제한, 운영자용 전역 호출/예산 안전장치를 둔다. 정확한 숫자는 배포 예산을 정한 뒤 확정한다.

## 8. 기존 20회 제한 처리

현재 `SESSION_MESSAGE_LIMIT=20`은 대화 길이 제한으로 유지한다. 새 대화를 만들면 다시 20개 메시지를 사용할 수 있지만, 성공한 AI 요청의 계정 누적 차감은 모든 대화를 합쳐 계속된다. UI와 오류 문구는 `이 대화의 남은 메시지`와 `계정의 남은 AI 요청`을 서로 다른 값으로 표시해야 한다. 고정 안내도 대화 메시지 수에는 포함될 수 있지만 계정 AI 쿼터에는 포함되지 않는다. 비AI endpoint와 제출 폭주는 별도 속도 제한으로 방어한다.

## 9. 사용자·관리자 화면

사용자 화면에는 로그인한 이메일, 누적 사용 `사용/한도`, 남은 횟수를 표시한다. AI 호출 전 한도 부족이면 무엇이 차감되는지와 운영자 문의 안내를 보여준다. 고정 안내와 이미지 재검색에는 차감 표시를 하지 않는다.

관리자는 다음 최소 기능만 갖는다.

- 초대 이메일 추가·취소
- 계정 활성·비활성
- 계정별 누적 한도 설정·증액·감액
- charged/reserved/실패 공급자 시도 조회

관리자 조정은 이전 원장을 수정하지 않고 감사 로그를 남긴다. 신규 계정 한도는 0이며 관리자가 지급한 뒤 사용할 수 있다. 최초 관리자는 배포 환경에 명시한 1개 Google 이메일이 검증 로그인에 성공했을 때만 admin으로 저장하는 일회성 부트스트랩을 권장하며, 실제 이메일과 부트스트랩 절차는 인증 단계 전에 확정한다.

## 10. 기존 익명 데이터

기존 익명 쿠키의 대화·개인 용어를 첫 Google 로그인에 자동 합치지 않는다. 공유 기기, 만료 쿠키, 잘못된 계정 로그인 때문에 다른 사람 데이터가 귀속될 수 있기 때문이다.

초기 데모 기본안은 로그인 계정에 새 owner를 제공하고 기존 로컬 개인 데이터는 그대로 보존하는 것이다. 향후 가져오기가 필요하면 유효한 기존 쿠키와 로그인 계정을 동시에 증명하고, 목록을 보여준 뒤 명시적으로 선택·확인하는 별도 기능으로 설계한다.

## 11. 단계별 구현 순서

각 단계는 구현·검증·사용자 검수 후 다음 단계로 진행한다.

1. 계정·초대·owner 연결 및 쿼터 reservation/charge/release DB 기반과 동시 요청 테스트
2. Google 로그인/콜백/로그아웃, 앱 세션과 초대 거부·비활성화 검증
3. 대화 LLM과 개인 용어 generator의 성공 차감 연결 및 장애 복구, 고정 안내·재검색 0차감 검증
4. 사용자 잔여 표시와 최소 관리자 초대·한도·비활성화 화면, 감사 로그
5. 전체 권한·쿼터 흐름과 격리된 배포 환경에서 약 10개 테스트 계정 운영 리허설

## 12. 핵심 수용 테스트

- 초대되지 않은 이메일, 미검증 이메일, 비활성 계정은 로그인할 수 없다.
- A 계정은 B의 대화·개인 용어·검색 기록·쿼터를 ID 추측으로 읽거나 바꿀 수 없다.
- 성공한 AI 대화와 성공한 개인 용어 초안은 각각 정확히 1회 차감된다.
- 고정 안내, 이미지 재검색, 실패, 내부 재시도, idempotent 재제출은 추가 차감되지 않는다.
- 남은 1회에 동시 요청 두 건이 들어오면 하나만 예약되고 다른 하나는 공급자 호출 전에 거부된다.
- worker 중단 뒤 reservation이 결과 상태에 맞게 복구되고 이중 차감되지 않는다.
- 새 대화·로그아웃·재로그인·다른 기기에서도 같은 계정 누적값이 유지된다.
- 계정 비활성화와 초대 취소는 기존 앱 세션에도 적용된다.
- 기존 공용 카탈로그, 그래프, 검색과 개인 용어 기능은 계정 전환 뒤에도 동일하게 동작한다.

## 13. 구현 전 열린 결정

1. 초대할 실제 이메일 목록과 계정별 최초 지급 횟수
2. 전역 운영자 안전한도와 계정·IP별 속도 제한 숫자
3. 최초 관리자 부트스트랩 이메일
