# 문맥 질문과 지원 범위 안내

현재 요청과 동일 대화의 검증된 기록을 받는 기존 해석 호출에서 질문도 생성한다. 별도 문구 생성 호출은 없다. 기존 회상 분류·검증 재시도 정책은 유지한다.

## 확인한 원인

- 앉기와 양손 조준 카드는 각각 활성이다. 앉아쏴 전용 조합 카드는 없다.
- 역할당 한 카드만 선택하며 검색어는 선택 카드의 고정 조각으로 만든다. 두 pose 카드를 합친 검색을 만들 수 없다. 별칭만 추가해도 이 제약은 해소되지 않는다.
- 이전에는 모델이 만든 clarifying_question을 resolver가 고정 질문으로 덮어썼다. 문맥은 전달되지만 반복 질문 차단은 없었다.
- 실제 모델의 개별 판단 이유는 저장된 최종 결과만으로 확정할 수 없다.

## 계약과 동작

- 정상 질문은 모델 문장을 유지한다. 내부 식별자·시스템 관련 표현·링크·마크업·과도한 길이는 고정 안전 문구로 복귀한다. 이 검사는 의미적 정확성을 보장하지 않는다.
- 새 해석 유형 catalog_limitation은 명확하지만 현 카탈로그/선택 계약으로 표현할 수 없는 요청에 사용한다. 기존 clarifying_question 필드에 지원 범위와 가능한 다음 선택지를 담는다.
- 최종 결과는 reference_guidance, reason_codes=[CATALOG_LIMITATION], user_message를 사용한다. reference_plan과 clarifying_question은 null이다. 새로운 검색이나 질문 대기 상태를 만들지 않는다.
- 최근 질문과 문장 정규화/유사도 검사에서 반복이면 reference_guidance, reason_codes=[CLARIFICATION_REPEATED]로 종료한다. pending_question을 지워도 최근 질문 검사는 유지한다. 기존 조건은 보존한다.
- 최근 기록은 기존 제한된 문맥 창이다. 다른 말로 바꾼 의미상 반복이나 창 밖의 과거 답변은 모델의 문맥 판단에 의존한다. 문구 생성 품질과 카탈로그 한계 판단은 실제 모델 평가 전까지 미검증이다.
- 프런트는 안내 문장을 표시하고 해당 턴에 새 레퍼런스 보기 버튼을 만들지 않는다. 기존 대화·결과는 유지한다. 저장 JSON의 추가 상태이며 DB 구조 변경은 없다. 기존 상태와 저장 결과도 계속 읽는다.

카탈로그·비용 설정·운영 DB·비밀키는 변경하지 않는다. 실제 모델 검증을 실행하려면 먼저 호출 수와 입력 범위를 별도로 승인받는다.

## 오프라인 검증

- 별도 로컬 테스트 DB와 외부 네트워크 차단: 백엔드 722개 통과.
- 프런트 82개 통과, live production 빌드 통과.
- 합성 브라우저: 문맥 질문, 지원 한계 안내, 반복 종료 안내 및 모바일 표시 통과. 모델 요청·외부 요청 0건.
- 독립 리뷰에서 발견한 pending 해제 후 반복 재발과 프롬프트 계약 충돌을 수정하고 재리뷰했다.
- 실제 Luna의 의미 판단과 문구 품질은 미검증이다. 별도 승인 시 실제 대화 대신 합성 입력으로 애매한 자세, 앞선 질문에 답한 문맥, 명확한 미지원 조합을 해석하는 3회 직접 호출을 최소 평가안으로 사용한다. 앱 전체 흐름의 회상 분류와 자동 재시도는 이 3회에 포함되지 않는다.
